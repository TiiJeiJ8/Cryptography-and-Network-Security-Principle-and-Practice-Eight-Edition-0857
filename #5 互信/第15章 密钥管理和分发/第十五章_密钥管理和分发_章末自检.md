# 第15章 密钥管理和分发 — 章末学习目标自检

## 1. 能否说明对称密钥分发的四种基本方式，并用 $n(n-1)/2$ 解释端到端成对密钥的规模问题？

A、B 之间分发对称密钥的四种方式：

1. A 选择密钥，以物理方式交给 B；
2. 第三方选择密钥，以物理方式交给 A 和 B；
3. 若 A、B 已共享旧密钥，一方用旧密钥加密新密钥发送给另一方；
4. 若 A、B 分别与第三方 C 建有加密连接，由 C 经这些连接把密钥传给双方。

前两种人工方式适合链接加密，但难以支持大规模端到端加密。若 $n$ 台主机之间任意两台都可能通信，所需成对密钥数量为：

$$\frac{n(n-1)}{2}$$

1000 个节点约需 50 万个密钥；10000 个用户或进程约需 5000 万个密钥，规模不可接受。第 3 种方式可减少人工分发，但旧密钥一旦泄露，攻击者可解开后续所有新密钥，形成连续泄露。大规模端到端加密通常采用第 4 种方式——每个用户只需与密钥分发中心共享一个长期密钥，由中心动态提供会话密钥。

## 2. 能否区分主密钥、会话密钥和临时密钥，并说明高层与低层密钥在使用频率、更新频率和保护强度上的差异？

| 密钥 | 生命期与用途 | 安全意义 |
| --- | --- | --- |
| **主密钥** | 通信实体与可信第三方长期共享，用于保护会话密钥的传递 | 使用频率低，但泄露会影响其保护的多个下层密钥 |
| **会话密钥** | 一次逻辑连接（如一次 TCP 连接）期间使用，结束后丢弃 | 频繁更换，限制单个密钥泄露的影响范围 |
| **临时密钥** | 只使用一次或生命期极短 | 进一步缩小密钥暴露窗口和受保护数据量 |

**层次关系**：高层密钥使用较少、更换较慢，需要更强的抗密码分析能力，用于加密分发下层密钥；低层密钥使用频繁、更换频繁，直接保护通信，可进一步派生临时密钥。低层密钥接触更多数据，频繁更换可限制密码分析材料；高层密钥虽使用少，但一旦泄露会连带破坏多个下层密钥，必须得到更强保护。

## 3. 能否区分 KTC 与 KDC，并说明二者分别由谁产生会话密钥？

设会话密钥为 $K_s$，A、B 与可信第三方共享的主密钥分别为 $K_{ma}$、$K_{mb}$。

| 第三方 | 谁产生 $K_s$ | 分发过程 |
| --- | --- | --- |
| **密钥转换中心（KTC）** | A 等通信实体自行生成或取得 | A 用 $K_{ma}$ 加密 $K_s$ 交给 KTC；KTC 解密后用 $K_{mb}$ 重新加密，直接交给 B 或经 A 转发 |
| **密钥分发中心（KDC）** | KDC 生成 | KDC 分别用 $K_{ma}$、$K_{mb}$ 加密 $K_s$，直接交给双方，或将两个密文都交给 A 由其转发 B 的部分 |

两者都需要认证参与方，并常用时间戳限制密钥交换时间或所分发密钥的生命期。核心区别在于会话密钥的产生者：KTC 只做"解密-重加密"的转换，KDC 则自己产生会话密钥。

## 4. 能否写出简单公钥会话密钥分发的恢复公式，并解释它为什么只能抵抗窃听、不能抵抗中间人攻击？

简单方案：

1. A 临时生成公私钥对 $\{\mathrm{PU}_a, \mathrm{PR}_a\}$，发送 $\mathrm{PU}_a \parallel \mathrm{ID}_A$；
2. B 生成会话密钥 $K_s$，发送 $E(\mathrm{PU}_a, K_s)$；
3. A 用私钥恢复：

$$D(\mathrm{PR}_a, E(\mathrm{PU}_a, K_s)) = K_s$$

会话结束后双方丢弃 $K_s$，会话前后都不需保存。

**只能抵抗被动窃听**：窃听者没有 $\mathrm{PR}_a$，无法解密 $E(\mathrm{PU}_a, K_s)$。

**不能抵抗中间人攻击**：该方案没有认证 A 最初发送的公钥确实属于 A。敌手 D 控制信道后：

1. 截获 A 的 $\mathrm{PU}_a$，替换为自己的 $\mathrm{PU}_d$ 发给 B；
2. B 用 $\mathrm{PU}_d$ 加密 $K_s$，D 用 $\mathrm{PR}_d$ 解密取得 $K_s$；
3. D 再用 $\mathrm{PU}_a$ 加密 $K_s$ 发给 A。

A、B 最终得到同一个 $K_s$，却不知道 D 也持有它，此后 D 只需被动窃听即可解密全部通信。**使用公钥加密并不自动认证公钥的所有者**。

## 5. 能否说明时变值、接收方公钥和发送方私钥在兼具保密性与认证的密钥分发方案中分别起什么作用？

在 A、B 已可靠获得彼此当前公钥的前提下：

1. A 用 B 的公钥加密 $\mathrm{ID}_A$ 和时变值 $N_1$；
2. B 用 A 的公钥加密返回 $N_1$ 和新时变值 $N_2$——返回 $N_1$ 证明 B 能解开第 1 条消息；
3. A 用 B 的公钥加密返回 $N_2$——B 据此认证 A；
4. A 选择 $K_s$，先私钥处理再公钥加密：

$$M = E(\mathrm{PU}_b, E(\mathrm{PR}_a, K_s))$$

5. B 依次恢复：

$$D(\mathrm{PU}_a, D(\mathrm{PR}_b, M)) = K_s$$

各要素作用：

| 要素 | 作用 |
| --- | --- |
| **接收方公钥 $\mathrm{PU}_b$（外层）** | 保证只有 B 能读取密钥，提供**保密性** |
| **发送方私钥 $\mathrm{PR}_a$（内层）** | 使 B 能确认密钥来自 A，提供**来源认证** |
| **时变值 $N_1, N_2$** | 把响应绑定到当前交互，防止重放攻击，提供**时效性**和双向认证 |

## 6. 能否比较公开发布、公开目录、公钥授权和公钥证书四种方法的信任依据、风险与代价？

| 方法 | 信任依据 | 主要风险或代价 |
| --- | --- | --- |
| **公开发布** | 无——用户直接广播公钥 | 任何人可冒名发布伪造公钥；攻击者可读取加密消息或伪造认证 |
| **公开可访问目录** | 可信管理员维护 $\{$名称, 公钥$\}$ 动态目录，注册和更新经安全认证 | 管理员私钥泄露或目录被篡改时，攻击者可假冒任意用户 |
| **公钥授权** | 在线管理员对公钥、原请求和时间戳签名 | 每次取钥依赖管理员，消息多、易成瓶颈；缓存需周期更新 |
| **公钥证书** | CA 对主体标识、公钥和时效信息签名，证书可经任何渠道传递 | 验证者必须可靠获得 CA 公钥，并检查有效期和撤销状态 |

公钥授权的签名响应包含三部分：B 的当前公钥、A 的原始请求（发现请求被替换）、原始时间戳（排除旧公钥重放）。证书机制的简化形式为：

$$C_A = E(\mathrm{PR}_{\text{auth}}, [T \parallel \mathrm{ID}_A \parallel \mathrm{PU}_a])$$

时间戳 $T$ 相当于截止日期，限制旧证书重放风险。

## 7. 能否列举并解释 X.509 证书的全部字段，并说明版本 1、2、3 与可选字段的关系？

| 字段 | 含义 |
| --- | --- |
| **版本号** | 默认 v1；出现发行商/主体唯一标识时为 v2；出现扩展时为 v3 |
| **证书序号** | 同一 CA 内唯一标识证书的整数 |
| **签名算法标识** | CA 签名所用算法及参数 |
| **发行商名称** | 创建并签署证书的 CA 名称 |
| **有效期** | 生效日期和终止日期 |
| **证书主体名** | 证书属主名称，持有对应私钥的主体 |
| **主体公钥信息** | 主体公钥、算法标识符和参数 |
| **发行商唯一标识** | 可选，名称复用时唯一标识 CA（v2 加入） |
| **证书主体唯一标识** | 可选，名称复用时唯一标识主体（v2 加入） |
| **扩展** | v3 加入的一个或多个可选扩展字段 |
| **签名** | 覆盖所有其他字段的 CA 数字签名及算法标识 |

版本演进关系：v1 包含基础字段；v2 在 v1 基础上增加两个可选唯一标识字段（实际较少使用）；v3 在 v2 基础上增加扩展字段，以支持邮件地址、URL、密钥用途限制、策略约束等。目录服务器只存取证书，不签发证书；证书由 CA 签名，攻击者无法不被发现地修改，因此目录无需特别防伪造保护。

## 8. 能否按顺序解释证书链的验证过程，并说明前向证书与后向证书的区别？

X.509 用 $Y\langle\langle X\rangle\rangle$ 表示 CA $Y$ 为主体 $X$ 签发的证书。若 A 信任 $X_1$，而 B 的证书由 $X_2$ 签发，A 使用证书链：

$$X_1\langle\langle X_2\rangle\rangle \; X_2\langle\langle B\rangle\rangle$$

验证顺序：
1. 用已信任的 $X_1$ 公钥验证 $X_1\langle\langle X_2\rangle\rangle$，取得可信的 $X_2$ 公钥；
2. 用 $X_2$ 公钥验证 $X_2\langle\langle B\rangle\rangle$，取得可信的 B 公钥。

长度为 $N$ 的一般链：

$$X_1\langle\langle X_2\rangle\rangle \; X_2\langle\langle X_3\rangle\rangle \; \cdots \; X_N\langle\langle B\rangle\rangle$$

链中每张证书都由上一阶段已验证的公钥检查。

每个 CA 的目录项包含两类证书：
- **前向证书**：其他 CA 为本 CA 签发的证书（从本 CA 指向信任链上游）；
- **后向证书**：本 CA 为其他 CA 签发的证书（从本 CA 指向下游）。

X.509 建议把 CA 按层次组织以便寻找证书路径。

## 9. 能否列出证书提前撤销的原因，并说明 CRL 的签名、更新时间、证书序号和撤销时间分别有什么作用？

证书在到期前撤销的三类原因：

1. 用户私钥被认为已经不安全；
2. 用户不再信任该 CA（主体名改变、证书废弃或未按 CA 规则签发）；
3. CA 证书被认为已经不安全。

每个 CA 维护**证书撤销表（CRL）**，由发行 CA 签名，包含：

| 字段 | 作用 |
| --- | --- |
| **发行商名称** | 标识签发 CRL 的 CA |
| **本次更新时间 / 下次更新时间** | 标明 CRL 的时效，验证者据此判断是否需要获取新 CRL |
| **证书序号** | 在同一 CA 内唯一标识被撤销证书，验证者比对证书序号即可查知是否撤销 |
| **撤销时间** | 记录撤销发生的时间，用于审计和争议处理 |
| **CA 签名** | 保证 CRL 本身不可伪造或篡改 |

验证者不仅要检查 CA 签名和有效期，还必须检查撤销状态。可本地缓存证书和 CRL 以减少目录访问，但缓存必须及时更新。

## 10. 能否概括 X.509 版本 3 的三类扩展，并解释危险指示、密钥使用和基本限制字段？

每个 v3 扩展包含扩展标识、**危险指示**（critical）和扩展值。若危险指示为 `TRUE` 而实现不能识别或处理该扩展，则必须把证书视为非法。

三类扩展：

| 类别 | 主要字段与作用 |
| --- | --- |
| **密钥和策略信息** | 授权密钥标识符（区分同一 CA 的不同密钥）、主体密钥标识符（区分主体密钥）、**密钥使用**（限定签名、密钥加密、数据加密等用途）、私钥使用期限、证书策略和策略映射 |
| **证书主体和发行商属性** | 主体可选名称和发行商可选名称（支持邮件地址、URL 等）、主体目录属性 |
| **证书路径约束** | **基本限制**（指出主体能否作为 CA，并可限制路径长度）、名称限制（约束后续主体名称空间）、策略限制（约束路径中的策略和策略映射） |

**密钥使用**扩展将公钥限定在特定用途（如只用于签名或只用于密钥加密），防止密钥滥用；**基本限制**扩展区分终端实体证书和 CA 证书，并可限制证书链最大长度，防止无限委派。

## 11. 能否列出 PKI 的五类基本组件，并用 Alice 获取 Bob 公钥的过程说明它们如何配合？

**公钥基础设施（PKI）**是管理证书和公私钥对的策略、流程、服务器平台、软件和工作站的集合。

| 组件 | 职责 |
| --- | --- |
| **终端实体** | 在证书作用范围内被认证的用户、设备、程序；也可是 PKI 服务的使用者或提供者 |
| **证书颁发机构（CA）** | 创建并分发证书，用签名把主体名称绑定到公钥；可为主体生成密钥，发布 CRL |
| **注册机构（RA）** | 可选组件，分担 CA 管理工作，通常验证申请注册和取证的终端实体身份 |
| **证书存储库** | 存储和检索证书、CRL，可采用 X.500/LDAP 目录或 FTP/HTTP |
| **信赖方** | 依靠证书数据作出安全决策的用户或代理 |

**Alice 获取 Bob 公钥的流程**：

1. Alice 通过可靠安全方式取得 CA 公钥（信任起点）；
2. Alice 查询存储库，检查 Bob 的证书是否已撤销；
3. 若未撤销，从存储库或 Bob 处取得证书；
4. 用 CA 公钥验证证书签名、有效期和相关状态；
5. 从通过验证的证书中取得 Bob 公钥；
6. 用该公钥加密发给 Bob 的数据；
7. 若 Bob 签署文档，Alice 用证书中 Bob 公钥验证签名。

## 12. 能否说明根 CA、从属 CA、预置根证书和证书验证路径之间的关系？

企业可能使用多个 CA 和多个存储库，CA 按层次组织：

- **根 CA**：位于层次顶端，是广泛信任的起点，为从属 CA 签发证书；
- **从属 CA**：由上级 CA 签发证书，可再为下级 CA 或终端实体签发证书；
- **预置根证书**：Web 浏览器、服务器、邮件客户端、智能手机等系统出厂时预置一组根 CA 的公钥证书，使这些根 CA 成为证书验证路径的**信任起点**。

验证路径从终端实体证书出发，沿签发关系逐级向上，直到到达一个预置的受信根 CA：

$$\text{Bob 证书} \leftarrow \text{从属 CA 证书} \leftarrow \cdots \leftarrow \text{根 CA（预置信任）}$$

信赖方用预置根公钥验证下一级 CA 证书，逐级向下，最终验证 Bob 证书。路径中每张证书的签名都由上一级已验证的公钥检查；基本限制扩展可约束路径长度和哪些主体可作为 CA。
