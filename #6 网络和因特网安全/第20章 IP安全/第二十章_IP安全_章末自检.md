# 第20章 IP安全 — 章末学习目标自检

---

## 1. 能否说明 IPsec 的应用、文档组成和六类主要安全服务？

**IPsec** 在 IP 层提供认证、保密性和密钥管理，可保护远程登录、客户端/服务器、电子邮件、文件传输和 Web 等所有上层应用，而不要求每个应用单独实现安全功能。典型应用包括分支机构 VPN、远程访问、企业外连网/内连网和增强电子商务安全。

**文档组成**：

| 文档 | 内容 |
| --- | --- |
| 架构（RFC 4301） | 总体框架和安全处理模型 |
| AH（认证头部） | 主要提供认证，现代新应用较少使用 |
| ESP（封装安全净荷） | 提供加密或加密/认证组合，现代应用优先使用 |
| IKE（因特网密钥交换） | 自动协商和管理 SA |
| 密码算法文档 | 各算法的具体规范 |

**六类主要安全服务**：访问控制、部分顺序完整性（反重放）、无连接完整性、保密性、数据源认证、有限流量保密性。

IPsec 的优势是对上层应用透明——安全处理在 IP 层完成，应用无需修改。

## 2. 能否比较 ESP 传输模式和隧道模式的保护范围、端点和 VPN 用途？

| 特性 | 传输模式 | 隧道模式 |
| --- | --- | --- |
| **加密范围** | IP 净荷（TCP/UDP 段或 ICMP 数据）和 ESP 尾部 | 整个内部 IP 数据包（内部头部+净荷+ESP 字段） |
| **IP 头部** | 保留原始 IP 头部，ESP 头部插在 IP 头与传输层段之间 | 添加新的外部 IP 头部，原始包作为外部包净荷 |
| **认证范围** | ESP 头部和密文，不保护原始 IP 头部 | 覆盖整个被封装的内部包 |
| **典型端点** | 支持 IPsec 的两台主机，端到端 | 安全网关之间或远程主机到网关 |
| **流量隐藏** | 有限，外部地址和长度仍可观察，可被流量分析 | 隐藏内部源/目的地址和流量结构，提供有限流量保密性 |
| **典型用途** | 主机到主机端到端通信，开销小 | 站点到站点 VPN、远程访问 VPN；内部主机可不实现 IPsec |

隧道模式的核心是**封装**：新 IP 头定义隧道入口和出口地址，封装包在公网上按外部头路由，中间路由器看不到内部结构；到达隧道终点后解封装，还原原始 IP 包并转发给真正目标。

## 3. 能否解释 SA 的单向性、SPI/目的地址/协议三元组和生命周期参数？

**安全关联（SA）** 是发送方和接收方之间的**单向逻辑连接**，规定该方向使用的安全服务、算法、密钥和生命周期。双向通信至少需要两个 SA（每个方向一个）。

每个 SA 由三元组唯一确定：

| 元素 | 含义 |
| --- | --- |
| **SPI（安全参数索引）** | 本地有意义的 32 位索引，由 AH/ESP 头部携带，接收方据此找到 SA |
| **IP 目的地址** | SA 的目的端点，主机或安全网关 |
| **安全协议标识** | 标明该 SA 使用 AH 还是 ESP |

SA 保存的生命周期参数包括：序号计数器及溢出标志、反重放窗口、AH/ESP 算法和密钥、SA 生命期（时间或字节数）、IPsec 模式（传输/隧道）、路径 MTU。

**序号不能回绕**：新 SA 序号从 0 开始，第一帧用 1；达到 $2^{32}-1$ 时必须终止 SA、协商新 SA 和新 SPI，避免序号重用破坏反重放机制。

## 4. 能否区分 SAD 保存的运行参数与 SPD 保存的流量策略和选择器？

| 数据库 | 性质 | 内容 | 回答的问题 |
| --- | --- | --- | --- |
| **SAD（安全关联数据库）** | 每个 IPsec 实现必须具备的"名义"数据库（功能必须有，实现方式自定） | 每个 SA 的 SPI、序号计数器、反重放窗口、认证/加密算法和密钥、生命周期、传输/隧道模式、路径 MTU | "已选 SA 具体怎么保护" |
| **SPD（安全策略数据库）** | 策略表 | 将流量子集映射到 `bypass`（绕过）、`discard`（丢弃）、`protect`（保护）三种动作，可指向一个或多个 SA | "哪些流量需要什么保护" |

**SPD 选择器**：远程/本地 IP 地址、下一层协议、操作系统用户标识、本地/远程 TCP/UDP 端口。

教材 SPD 示例体现**差异化精细管控**思想：IKE（UDP 500）和 ICMP 绕过；内联网网段和指定服务器走 ESP 保护；HTTPS（TCP 443）绕过以避免双重加密；未授权 DMZ 网段直接丢弃；普通因特网流量绕过。安全策略不能一刀切。

## 5. 能否按顺序描述 IPsec 对出站和入站数据包的处理？

**出站数据包**：

1. IPsec 用数据包选择器（地址、协议、端口）查询 SPD；
2. 无匹配项：丢弃并报告错误；
3. 匹配 `bypass`：直接转发；匹配 `discard`：丢弃；匹配 `protect`：继续；
4. 查询 SAD：若无匹配 SA，调用 IKE 协商建立带密钥的新 SA；
5. 按 SAD 规定执行 ESP/AH 处理（加密、认证、传输/隧道封装），发送数据包。

**入站数据包**：

1. 根据 IPv4 协议字段或 IPv6 下一个头部识别普通、ESP 或 AH 数据包；
2. **普通数据包**：查询 SPD，只有策略允许 `bypass` 时才剥离 IP 头交给上层，否则丢弃；
3. **安全数据包**：按 SPI（+目的地址+协议）查询 SAD，找不到 SA 则丢弃；找到则执行认证、反重放检查、解密和解封装；
4. 剥离 IPsec 头部，把恢复的净荷交给 TCP/UDP 等上层协议。

关键不对称：出站先查 SPD 定策略再查 SAD 取参数；入站的安全包直接按 SPI 查 SAD，普通包才查 SPD。

## 6. 能否写出 ESP 字段、加密范围、ICV 计算顺序、填充用途和反重放窗口逻辑？

**ESP 数据包格式**（按顺序）：

| 字段 | 说明 |
| --- | --- |
| SPI（4 字节） | 标识 SA |
| 序号（4 字节） | 单调递增，防重放 |
| 净荷数据（变长） | 加密后的传输层段或整个内部 IP 包；需要同步时开头显式携带 IV |
| 填充（0–255 字节） | 见下 |
| 填充长度（1 字节） | 填充字节数 |
| 下一个头部（1 字节） | 净荷中的协议类型 |
| ICV（变长，可选） | 完整性检查值 |

**加密范围**：净荷数据、填充、填充长度、下一个头部四部分被加密。

**ICV 计算顺序**：先加密，再对 ESP 头部（SPI、序号）和密文计算 ICV；ICV 不覆盖自身。组合认证加密算法（如 AES-GCM）可把完整性标签编码在密文结构中。

**填充的三种用途**：
1. 满足分组密码块长对齐要求；
2. 使填充长度和下一个头部字段在 32 位字中右对齐；
3. 隐藏真实净荷长度（流量保密性）。

**反重放窗口逻辑**：窗口默认大小 $W=64$，右边缘为当前已收最大合法序号 $N$：
- 窗口左侧（过旧）的包：直接丢弃；
- 窗口内的包：先验证完整性，通过且对应位未标记则接受并标记，重复或验证失败则丢弃；
- 窗口右侧（更新）的包：验证通过后接受，并把窗口右边缘推进到该序号。

## 7. 能否比较传输邻接、隧道迭代和四种基本 SA 部署组合？

单个 SA 只能实现 AH 或 ESP 之一，需要多种服务时使用 **SA 束**。两种组合方法：

| 组合方法 | 机制 | 特点 |
| --- | --- | --- |
| **传输邻接** | 在同一 IP 数据包上依次套用多个传输层协议（如内层 ESP、外层 AH） | 不经过隧道，通常只进行一级组合 |
| **隧道迭代** | 通过多个 IP 隧道嵌套安全协议，各层隧道可在不同 IPsec 节点终止 | 支持多层嵌套，适合多跳安全域 |

**认证与加密顺序的语义差异**：ESP 自带认证通常是"先加密后认证"；用内部 AH 传输 SA + 外部 ESP 隧道 SA 可实现"先认证后加密"——既隐藏内部认证数据，又能在目的端取得内部认证结果。

**四种基本部署**：
1. 主机到主机的端到端 SA（传输模式）；
2. 仅安全网关之间的隧道 VPN（隧道模式）；
3. 网关隧道之上再叠加端到端 SA（隧道+传输）；
4. 远程主机经隧道访问企业防火墙后的系统（远程访问 VPN）。

## 8. 能否解释 IKE cookie、nonce、DH、认证方法、IKE SA 和 CREATE_CHILD_SA 的作用？

IKEv1 体系包括 Oakley 密钥确定协议和 ISAKMP 框架；IKEv2 将二者整合。IKE 基于 Diffie-Hellman 但做了四项增强：

| 机制 | 作用 |
| --- | --- |
| **cookie** | 依赖双方地址、端口和本地秘密生成，可验证而无需服务器保存状态，抵御伪造源地址造成的阻塞（DoS）攻击 |
| **nonce** | 随机数，防止重放并参与密钥和认证材料计算 |
| **DH 交换** | 协商 DH 参数组并交换公钥，得到共享密钥 $K = (Y_B)^{X_A} = (Y_A)^{X_B} = \alpha^{X_A X_B} \bmod q$ |
| **身份认证** | 数字签名、公钥加密或预共享对称密钥认证交换，防止 DH 中间人攻击 |

**两类 SA 的关系**：
- **IKE SA**：初始交换第一对消息（IKE_SA_INIT）协商算法、nonce 和 DH 值后建立，用于保护后续所有 IKE 控制消息；
- **CHILD_SA（IPsec SA）**：第二对消息（IKE_AUTH）在已加密的 IKE SA 内交换标识和认证数据，建立第一个用于保护业务数据的 IPsec SA。建立首个数据 SA 共需 **4 条消息**。
- **CREATE_CHILD_SA**：后续用于建立更多子 SA，或为现有 SA 重新生成密钥（密钥更新）。

IKE 本身不加密业务数据，而是为 ESP/AH 提供安全上下文；SA 安装后由 ESP/AH 接管数据面保护。IKE 消息用通用净荷头部的"下一个净荷"字段串联多个净荷（SA 建议、密钥交换、nonce 等），临界位指示未知净荷应跳过还是拒绝。

## 9. 能否按用途选择并比较 IPsec 的加密、完整性、PRF、密钥交换和认证套件？

| 功能 | 典型选择 | 选择依据 |
| --- | --- | --- |
| **加密** | AES；优先 AES-GCM 等认证加密模式 | 分组长度和密钥强度满足生命周期安全要求 |
| **完整性/数据源认证** | 基于 HMAC 的算法（如 HMAC-SHA-256/384），或认证加密内置标签 | 认证加密可一步完成加密和完整性，减少处理环节 |
| **伪随机函数（PRF）** | IKE 中用于从共享秘密、nonce 和上下文派生密钥材料 | 输出长度和强度与密钥层次匹配 |
| **密钥交换** | Diffie-Hellman 或椭圆曲线 DH（ECDH）参数组 | ECDH 参数更短、效率更高；临时 DH 提供前向安全 |
| **身份认证** | 数字签名、公钥加密或预共享对称密钥 | 证书适合大规模部署，预共享密钥适合小规模固定对端 |

IPsec 算法套件可协商，应随安全要求、实现能力和生命周期更新。安全性来自算法、密钥、SA 参数、SPD/SAD 策略配置、身份认证和反重放窗口的**共同约束**——只启用强算法而错误配置策略或认证，仍不能形成有效保护。
