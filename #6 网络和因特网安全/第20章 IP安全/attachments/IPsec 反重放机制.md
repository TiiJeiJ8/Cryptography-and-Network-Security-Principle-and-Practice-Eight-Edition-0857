# IPsec 反重放机制专题笔记

## 一、概述

重放攻击（Replay Attack）是指敌手截获一个经过认证的数据包后，在某个时刻将其重新传送到目的站点的行为。重复接收经过认证的 IP 数据包可能会中断服务或产生无法预料的结果。IPsec 通过**序列号（Sequence Number）** 与**滑动窗口（Sliding Window）** 的组合机制来防御此类攻击。

该机制在 RFC 4301（IPsec 架构）和 RFC 4303（ESP 规范）中定义，是 IPsec 提供的“部分序列完整性（Partial Sequence Integrity）”服务的一种形式。所有 ESP 实现都必须支持反重放服务，但其使用可由接收方在每个安全关联（SA）上单独启用或禁用。

> **术语说明**：反重放机制在 AH 和 ESP 中均可使用。由于 ESP 是当前 IPsec 的主流实现，AH 已不推荐在新应用中使用，本笔记以 ESP 为讨论对象。

## 二、核心机制：序列号 + 滑动窗口 + 位图

### 2.1 发送方：序列号计数器

每个安全关联（SA）的发送方维护一个**单调递增的 32 位序列号计数器**：

- 建立新 SA 时，计数器初始化为 0。
- 每发送一个数据包，计数器加 1，第一个数据包的序列号为 1。
- 序列号字段是 ESP 头部的**必填字段**，始终存在。
- 当序列号达到 $2^{32} - 1$ 时，**不允许回绕（rollover）** 。发送方必须终止当前 SA，并重新协商一个新的 SA。

**设计意图**：序列号的单调递增性质使得每个数据包在 SA 的生命周期内拥有唯一标识，为接收方的重放检测提供了基础。

### 2.2 接收方：滑动窗口与位图

接收方维护一个**大小为 W 的滑动窗口**（默认 $W = 64$）。该窗口在逻辑上由两部分组成：

1. **右边缘（$N$）** ：迄今为止接收到的**最大合法序列号**。
2. **左边缘（$N - W + 1$）** ：当前窗口的下界。

窗口覆盖的序号范围为 $[N - W + 1, N]$。任何序号小于左边缘的数据包被视为“过期”，直接丢弃。

窗口内部维护一个**位图（Bitmap）** ，长度为 $W$ 位。位图中的每个比特对应窗口内的一个序列号：
- **0**：该序列号尚未被接收过。
- **1**：该序列号已被成功接收并验证。

> **位图的工程意义**：位图使得接收方能够以 $O(1)$ 的时间复杂度完成“该序号是否已被接收”的查询，而无需遍历历史记录。在高速网络环境中，这一设计对性能至关重要。

### 2.3 窗口操作逻辑

教材图 20.5 展示了窗口操作的基本流程。以下为完整的处理逻辑：

**情况一：序号位于窗口左侧（$Seq < N - W + 1$）**

数据包被视为**过期**，直接丢弃，不做完整性校验。此为该数据包的最终处理结果。

**情况二：序号位于窗口内（$N - W + 1 \le Seq \le N$）**

1. 查询位图中对应比特位。
2. 若该位**已被标记为 1** → 该数据包是**重放攻击**，直接丢弃。
3. 若该位**为 0** → 该序号尚未被接收过，继续执行完整性校验（ICV 验证）。
4. 完整性校验通过 → 接受数据包，**将位图中对应比特标记为 1**。
5. 完整性校验失败 → 丢弃数据包（该数据包可能被篡改，也可能是重放攻击者伪造的）。

**情况三：序号位于窗口右侧（$Seq > N$）**

1. 执行完整性校验（ICV 验证）。
2. 校验失败 → 丢弃数据包。
3. 校验通过 → 接受数据包。
4. **窗口右边缘更新为 $Seq$ **，即 $N = Seq$。
5. 窗口整体向右滑动 $Seq - N$ 个位置。
6. 位图同步左移：超出新窗口左边缘的旧标记被清除，新进入窗口的比特位初始化为 0。
7. 将序号 $Seq$ 对应的比特位标记为 1。

### 2.4 伪代码示例

RFC 4303 附录 A 2.3 提供了反重放检查的伪代码实现。以下为简化后的核心逻辑：

```
If (Seq < N - W + 1)
    Reject packet (out of window)
Else If (Seq <= N)
    If (bitmap[Seq] == 1)
        Reject packet (replay)
    Else
        If (integrity_check(packet) == FAIL)
            Reject packet
        Else
            bitmap[Seq] = 1
            Accept packet
Else // Seq > N
    If (integrity_check(packet) == FAIL)
        Reject packet
    Else
        N = Seq
        Shift bitmap left by (Seq - N_old)
        bitmap[Seq] = 1
        Accept packet
```

## 三、关键设计参数

### 3.1 窗口大小 W

- **默认值**：64。
- **设计考量**：窗口大小必须足以容纳网络中可能发生的**乱序交付（Out-of-Order Delivery）** ——即序号较大的数据包先于序号较小的数据包到达。
- **调整原则**：在乱序严重的网络环境中，应增大窗口大小以避免误判合法数据包为过期包；在严格按序交付的环境中，窗口可缩小至 1。
- **上限**：$W$ 不能超过 $2^{32} - 1$。

### 3.2 序列号的生命周期

| 阶段 | 发送方行为 | 接收方行为 |
| :--- | :--- | :--- |
| SA 建立 | 计数器置 0 | 窗口初始化，位图清零 |
| 正常通信 | 每包计数器+1 | 按窗口规则处理 |
| 计数器达到 $2^{32}-1$ | **必须终止 SA，重新协商** | — |
| SA 终止 | 销毁计数器 | 销毁窗口和位图 |

## 四、异常情况与扩展机制

### 4.1 扩展序列号（ESN）

对于需要传输超过 $2^{32}$ 个数据包的高流量 SA，IPsec 定义了**扩展序列号（Extended Sequence Number, ESN）** 机制：

- 发送方和接收方维护 **64 位**的完整序列号计数器。
- 但在数据包中**仅传输低 32 位**（ESP 头部的 Sequence Number 字段）。
- 高 32 位不随包传输，而是通过算法在接收方推断得出，并参与完整性校验值（ICV）的计算。

**推断算法**（RFC 4303 附录 A 2.2）：

设 $T_h$ 为当前高 32 位，$T_l$ 为当前低 32 位，$W$ 为窗口大小。收到包的低 32 位为 $Seq_l$：

- **情况 A**（$T_l \ge W - 1$）：若 $Seq_l \ge T_l - W + 1$，则 $Seq_h = T_h$；否则 $Seq_h = T_h + 1$。
- **情况 B**（$T_l < W - 1$）：若 $Seq_l \ge T_l - W + 1$，则 $Seq_h = T_h - 1$；否则 $Seq_h = T_h$。

### 4.2 计数器溢出处理

- **标准 32 位模式**：计数器达到 $2^{32} - 1$ 时**不允许回绕**，必须终止 SA 并重新协商。
- **ESN 模式**：64 位计数器在正常使用周期内不会溢出（$2^{64}$ 在工程上视为无限）。
- **禁用反重放时**：若接收方在某 SA 上禁用了反重放服务，发送方允许计数器回绕，允许使用重复序列号。

### 4.3 极端丢包后的同步恢复

如果在一个 SA 上连续丢失 $2^{32}$ 个以上的数据包，发送方和接收方将失去高 32 位的同步。此时：

- 后续数据包的完整性校验将失败并被丢弃。
- RFC 4303 建议实现一种重同步机制来应对此情况。
- 在实践中，这种规模的丢包通常会被上层协议（如 TCP 的超时重传）检测到，从而在 IPsec 需要介入之前停止传输。

## 五、安全边界：为什么不能通过改序号绕过反重放？

你之前提出的问题——“如果攻击者更改数据包的序号，能否绕过反重放？”——触及了 IPsec 安全设计的核心。答案是**不能**，原因在于**完整性保护覆盖了序号字段**。

### 5.1 序号处于完整性保护范围之内

在 ESP 中，**完整性校验值（ICV）** 的计算覆盖以下字段：

- ESP 头部（含 SPI 和**序号**）
- 加密后的密文（净荷数据、填充、填充长度、下一个头部）

这意味着**序号是“带锁”的**。任何对序号的修改都会导致接收方计算出的 ICV 与数据包中携带的 ICV 不匹配。

### 5.2 攻击者的两种尝试均会失败

| 攻击动作 | 接收方检查点 | 结果 |
| :--- | :--- | :--- |
| 仅更改序号，不改 ICV | 完整性校验 | **失败**，ICV 不匹配，数据包被丢弃 |
| 更改序号并重新计算 ICV | 完整性校验 | **失败**，攻击者不知道共享的认证密钥，无法生成合法 ICV |

**核心原则**：在密码学意义上，不掌握密钥就无法为篡改后的数据生成有效的认证标签。这是 HMAC 等消息认证码算法的基本安全属性。

## 六、禁用反重放的特殊情况

RFC 4301 指出，在某些场景下可以禁用反重放服务：

- **手动密钥管理的 SA**：由于缺乏动态密钥协商机制，反重放窗口的管理可能不适用。
- **多发送方组播 SA**：多个发送方各自维护序列号计数器时，难以保证全局单调递增。

但在这些情况下，**序列号字段仍然存在**（ESP 头部必填），只是接收方忽略反重放检查。

## 七、总结

IPsec 的反重放机制通过**三层防护**实现：

1. **序列号单调性**：每个数据包在 SA 生命周期内拥有唯一标识，为检测重复提供基础。
2. **滑动窗口**：限定可接受序号的范围，淘汰过期数据包。
3. **位图标记**：在窗口内精确记录每个序号是否已被接收，杜绝同一序号被重复接受。

**完整性保护**是贯穿上述所有机制的底层保障——序号字段本身受到 ICV 的密码学保护，攻击者无法在不被发现的前提下篡改序号。这一设计确保了反重放机制不会被“改序号”这类简单攻击所绕过。
