# 第19章 电子邮件安全 — 章末学习目标自检

## 1. 能否画出 MUA、MSA、MTA、MDA、MS 的邮件路径，并说明 DNS 和 ADMD 的作用？

因特网邮件架构由用户侧的消息用户代理和传输侧的消息处理服务组成：

| 组件 | 全称 | 职责 |
| --- | --- | --- |
| **MUA** | 消息用户代理 | 代表用户生成、格式化、提交、接收、存储或显示邮件 |
| **MSA** | 邮件提交代理 | 接收 MUA 提交的消息，执行托管域策略和因特网标准要求 |
| **MTA** | 消息传输代理 | 在应用层评估路由并中继邮件，直到到达目标 MDA，同时添加路径信息 |
| **MDA** | 邮件投递代理 | 将消息从邮件处理系统投递到消息存储 |
| **MS** | 消息存储 | 长期保存邮件，可位于远程服务器或与 MUA 同机 |

完整邮件路径：

```text
发送方 MUA
  └─ SUBMISSION/SMTP → MSA
      └─ SMTP → 发送 MTA
          └─ SMTP → 中继 MTA（可有多个）
              └─ SMTP → 接收 MTA
                  └─ MDA → MS
                      └─ POP3/IMAP → 接收方 MUA
```

**ADMD（行政管理域）**是执行特定邮件策略和信任决策的邮件提供者，如企业 IT 部门或 ISP。**DNS** 提供主机名与地址映射：发送 MTA 查询接收域的 **MX 资源记录**找到下一跳接收 MTA。

## 2. 能否区分 SMTP/ESMTP/SUBMISSION 与 POP3、IMAP 的方向、功能和端口？

| 协议 | 方向 | 功能 | 端口 |
| --- | --- | --- | --- |
| **SMTP** | 推送/中继 | 运行在 TCP 上的文本型协议，负责邮件提交、中继和传输；四字母命令码，三位数字应答 | TCP 25 |
| **ESMTP** | 同 SMTP | SMTP 后续修订增加的扩展命令（如认证、STARTTLS、流水线） | 25 |
| **SUBMISSION** | MUA → MSA | 从 SMTP 演化的专用提交标准，使用独立端口，要求访问授权 | TCP 587 |
| **POP3** | 拉取 | 用户代理从服务器下载、检索和删除邮件，命令较简单 | TCP 110（POP3S 995） |
| **IMAP** | 双向同步 | 访问并**管理服务器上**的邮件，认证能力更强，支持多文件夹、服务器端搜索等 POP3 不支持的功能 | TCP 143（IMAPS 993） |

SMTP 解决"如何把邮件送达"，POP3/IMAP 解决"用户如何访问已投递邮件"。中继 MTA 收到消息后转为下一段连接的 SMTP 客户端。这些协议均可在 TLS 上运行。

## 3. 能否解释原始 SMTP/RFC 5322 为什么不能可靠支持二进制、多语言和多媒体邮件？

RFC 5322 定义传统文本邮件格式：若干头部行（`From`、`To`、`Subject`、`Date`、`Message-ID`）和正文以空行分隔，但内容格式以 7 位 ASCII 文本为基础。六类具体限制：

1. 不能直接传输可执行文件和其他二进制对象；
2. 不能直接传输用高位字符表示的民族语言文本（如中文）；
3. 某些 SMTP 服务器会拒绝超长消息；
4. ASCII 与 EBCDIC 网关可能使用不一致的字符映射；
5. SMTP 与 X.400 网关难以处理非文本数据；
6. 不完全合规的实现可能改变回车换行、截断长行、去除尾随空白、填充行或转换制表符，破坏数据。

**MIME** 是 RFC 5322 框架的扩展，在兼容前提下解决这些问题：扩展邮件头部、标准化多媒体内容格式、定义不会轻易被传输系统改写的传输编码。

## 4. 能否列出 MIME 五个头部字段、七类内容、常见 multipart/message 子类型及六种传输编码？

**五个头部字段**（前三个必须支持）：

| 字段 | 含义 |
| --- | --- |
| `MIME-Version` | 必须为 `1.0` |
| `Content-Type` | 媒体类型、子类型及参数，指导接收方处理内容 |
| `Content-Transfer-Encoding` | 正文为适应传输采用的编码 |
| `Content-ID` | 唯一标识 MIME 实体（可选） |
| `Content-Description` | 为不可直接阅读对象提供文本说明（可选） |

**七类基本内容类型**：`text`、`multipart`、`message`、`image`、`audio`、`video`、`application`。

**multipart 子类型**：

| 子类型 | 用途 |
| --- | --- |
| `multipart/mixed` | 按顺序组合多个独立部分 |
| `multipart/parallel` | 各部分顺序不重要，可并行显示 |
| `multipart/alternative` | 同一信息的多种表示，按优先级递增排列 |
| `multipart/digest` | 每部分都是带头部的 RFC 5322 消息 |

**message 子类型**：`message/rfc822`（封装完整邮件）、`message/partial`（大消息分片，靠标识、序号和总片数重组）、`message/external-body`（正文只给外部对象访问指针）。multipart 用不会出现在正文中的边界字符串分隔各部分。

**六种传输编码**：

| 编码 | 作用 |
| --- | --- |
| `7bit` | 较短 ASCII 文本行（描述性质） |
| `8bit` | 允许高位置位字节，行仍较短 |
| `binary` | 允许任意字节和任意行长 |
| `quoted-printable` | 十六进制表示不安全字符，适合以可打印文本为主的数据 |
| `base64` | 每 3 字节映射为 4 个可打印 ASCII 字符，适合二进制数据 |
| `x-token` | 厂商专用非标准编码 |

## 5. 能否描述 S/MIME 的数字签名、混合加密、压缩、邮件兼容性、内容类型和证书处理？

S/MIME 是 MIME 的安全增强，借助 CMS（加密消息语法）处理 MIME 实体，典型算法为 RSA/SHA-256 和 AES-128/CBC。

**四类基本服务**：

| 服务 | 过程 | 性质 |
| --- | --- | --- |
| **数字签名** | 计算 SHA-256 摘要，用发送方 RSA 私钥签名 | 发送方认证、完整性、不可抵赖 |
| **消息加密（混合加密）** | 随机生成一次性内容加密密钥，用 AES-128/CBC 加密消息，再用每个接收方 RSA 公钥加密内容密钥 | 保密性和密钥分发 |
| **压缩** | 在签名和加密前后按规则压缩 | 节省传输与存储空间 |
| **邮件兼容性** | 对二进制安全对象执行 base64 转换 | 适配只接受 ASCII 的邮件系统 |

每条消息使用独立一次性内容密钥，避免用低效公钥算法直接加密大消息，适应邮件存储转发、不便实时握手的特点。

**顺序规则**：签名后加密会隐藏签名者身份并保留明文签名；有损压缩必须**先压缩再签名**；不建议压缩二进制加密数据，但可压缩其 base64 表示。

**CMS 四种内容类型**：`Data`、`SignedData`、`EnvelopedData`、`CompressedData`。
- EnvelopedData：每接收方一个 `RecipientInfo`（用其公钥加密的会话密钥）；
- SignedData：`SignerInfo` 记录证书、摘要算法、签名算法和签名值，可携带证书链；
- **透明签名**：使用 `multipart/signed`，第一部分是可读正文，第二部分是分离式签名 `application/pkcs7-signature`，非 S/MIME 客户端仍可读正文；
- 注册请求用 `application/pkcs10`；仅含证书消息携带证书或 CRL，`SignerInfo` 为空。

**证书处理**：使用 X.509v3 证书，MUA 需生成并保护密钥对、向 CA 注册、维护本地证书和 CRL。RFC 2634 增强服务包括签收收据、安全标签、邮件列表代理加密、签名证书属性。

## 6. 能否说明 STARTTLS 的升级过程、逐跳保护边界、降级攻击和证书验证问题？

**升级过程**：
1. 双方先建立普通 SMTP TCP 连接，协商扩展能力（EHLO）；
2. 若双方都宣传支持 STARTTLS，客户端发送 `STARTTLS` 命令；
3. 服务器同意后在**同一 TCP 连接**上进行 TLS 握手；
4. 握手完成后，SMTP 信封、命令和消息全部在 TLS 中传输。类似机制也用于 POP3/IMAP。

**逐跳保护边界**：STARTTLS 保护的是**当前相邻实体之间的链路**（MUA—MSA 或 MTA—MTA）。邮件经多个中继时每一跳需分别建立 TLS，中继服务器上仍可见明文；它不像 S/MIME 那样让保护随消息保持到最终 MUA（端到端）。

**两个主要风险**：
- **降级攻击**：攻击者破坏 TLS 能力宣传（删除 EHLO 响应中的 STARTTLS 标识），使双方误以为对方不支持而回退到明文；
- **证书验证不可靠**：SMTP 实践中可能接受自签名或名称不匹配的证书，使服务器认证失效。

DANE 用经 DNSSEC 签名的 TLSA 记录声明必须加密并约束证书，从而补强 STARTTLS。

## 7. 能否解释 DNSSEC 的四类安全资源记录、信任链和 TLSA 四种证书用途？

**DNSSEC** 由区管理机构为资源记录集合（RRset）生成数字签名，解析器验证签名，提供数据源认证和完整性，无需信任中间 DNS 服务器或缓存。四类新资源记录：

| 记录 | 作用 |
| --- | --- |
| **DNSKEY** | 携带区公钥 |
| **RRSIG** | 携带 RRset 的数字签名 |
| **DS** | 连接父区和子区的授权签名者（信任链锚点） |
| **NSEC** | 对名称或记录不存在的否定应答进行认证 |

**信任链**：从根区等信任锚开始，经父区验证子区（DS 记录衔接），逐级建立到目标应答区的链。

**DANE/TLSA** 使用 DNSSEC 将 X.509 证书或公钥绑定到域名，减少全球 CA 体系中任一被破坏 CA 的广泛影响。TLSA 记录含证书用途、选择器、匹配类型和证书数据四字段。四种证书用途：

| 用途 | 含义 |
| --- | --- |
| **PKIX-TA** | 限制可为服务证书背书的 CA，同时要求 PKIX 链验证到客户端可信根 |
| **PKIX-EE** | 限制服务所用的终端实体证书，同时要求 PKIX 链验证 |
| **DANE-TA** | 由域管理者指定新信任锚，可使用域自己的 CA |
| **DANE-EE** | 直接信任域颁发的服务证书，不依赖第三方 CA 根 |

选择器决定匹配完整证书还是公钥；匹配类型可为精确匹配、SHA-256 或 SHA-512 哈希。S/MIME 场景用格式相似的 SMIMEA 记录把证书与邮件地址所属域关联。

## 8. 能否根据发送 IP、SMTP 信封域、SPF 机制和修饰符判断授权结果？

SPF 让发送域在 DNS TXT 记录中声明哪些主机/IP 有权在 SMTP `MAIL FROM` 或 `HELO` 身份中使用该域。接收方在接收正文前比对实际连接 IP。

**机制**：

| 机制 | 匹配规则 |
| --- | --- |
| `ip4`/`ip6` | 指定授权 IPv4/IPv6 地址或网段 |
| `mx` | 域 MX 记录所列主机也是授权发送方 |
| `include` | 递归引用其他域的 SPF 策略（如第三方邮件服务） |
| `all` | 匹配此前未匹配的所有地址（通常放最后） |

**修饰符与结果**：

| 修饰符 | 结果 | 处理 |
| --- | --- | --- |
| `+`（默认） | 通过 | 接受 |
| `-` | 硬失败 | 不允许该来源代表域发送，拒绝 |
| `~` | 软失败 | 接收但标记并仔细检查 |
| `?` | 中性 | 策略未表态 |

判定规则：查不到 SPF 记录或记录格式错误时默认接收；其余按从上到下第一个匹配的机制及其修饰符决定。注意 SPF 检查的是**信封身份**而非用户可见的 `From` 头部，两者可不同，因此 SPF 不能独立解决可见发件人欺骗，需 DMARC 对齐。

## 9. 能否说明 DKIM 的签名位置、规范化、关键标记、DNS 公钥查询及与 S/MIME 的区别？

**签名位置**：DKIM 是域级签名，签名 ADMD 内的授权模块（MUA、MSA 或 MTA）用**域私钥**对消息正文和选定的 RFC 5322 头部签名，签名放入 `DKIM-Signature` 头部，对终端用户透明。

**规范化**：签名前对头部和正文分别执行 `simple`（几乎不改）或 `relaxed`（规整空格、折叠、大小写）规范化，减少传输中正常变换导致的验证失败。

**关键标记**：

| 标记 | 含义 |
| --- | --- |
| `v` | DKIM 版本 |
| `a` | 签名算法，如 `rsa-sha256` |
| `c` | 头部/正文规范化算法 |
| `d` | 签名域标识符（SDID） |
| `s` | 密钥选择器，用于在 DNS 中定位正确公钥 |
| `h` | 被签名的头部字段列表 |
| `bh` | 规范化后正文的哈希值 |
| `b` | base64 格式签名值 |

**DNS 公钥查询**：验证方按选择器 `s` 和签名域 `d` 构造 DNS 查询名取得域公钥，验证签名后结合签名域信誉和本地过滤策略处理。

**与 S/MIME 的边界区别**：

| 对比 | S/MIME | DKIM |
| --- | --- | --- |
| 密钥归属 | 用户级密钥 | 管理域级密钥 |
| 保护范围 | 端到端消息内容，要求双方客户端支持 | 该域发出的全部邮件，可覆盖发送相关头部 |
| 实施位置 | 通信双方 MUA | MSA/MTA，对用户透明 |

DKIM 能证明持域私钥一方对邮件负责并检测被签名内容修改，但不自动保证可见 `From` 域与签名域一致，也不能阻止拥有合法签名域的恶意发送者。

## 10. 能否区分 SPF、DKIM、DMARC 的认证对象，并说明 DMARC 对齐、策略、接收流程和两类报告？

**三种身份对象**：

| 协议 | 认证对象 |
| --- | --- |
| **SPF** | SMTP 信封中的 `MAIL FROM`/`HELO` 域与发送 IP 的授权关系 |
| **DKIM** | `d=` 指定的签名域及被签名的正文和头部 |
| **DMARC** | 用户可见的 RFC 5322 `From` 域，并要求它与 SPF 或 DKIM 的认证域**对齐** |

**标识符对齐**：
- **宽松对齐（`r`，默认）**：认证域与 `From` 域属于同一组织域即可（如 `mail.example.com` 对齐 `example.com`）；
- **严格对齐（`s`）**：必须精确匹配。由 `aspf`/`adkim` 标记分别控制。

**策略（DNS TXT 记录，`tag=value` 分号分隔）**：

| 标记 | 作用 |
| --- | --- |
| `v` | 版本，必须为第一个元素 |
| `p` | 主策略：`none`（仅监控）、`quarantine`（隔离）、`reject`（拒绝） |
| `rua`/`ruf` | 汇总报告/鉴定报告接收 URI |
| `ri` | 汇总报告间隔，默认 86400 秒 |
| `pct` | 应用策略的邮件百分比，默认 100 |
| `sp` | 子域策略；`fo` 触发失败报告条件 |

推荐渐进部署：先 `p=none` 收集报告，再逐步升到 `quarantine`、`reject`。

**接收流程**：黑名单/信誉检查 → 提取唯一 `From` → 查询 DMARC → 验证至少一个 DKIM 签名 → 执行 SPF → 检查身份对齐 → 取得适用策略 → 形成通过/失败结论 → 按本地策略投递、隔离或拒绝并收集报告数据。

**两类报告**：
- **汇总报告（rua）**：周期性统计策略结果、SPF/DKIM 结果、对齐情况、消息总数，评估整体部署效果；
- **鉴定报告（ruf）**：针对具体失败消息提供头部、对齐和投递结果等取证信息，帮助修复配置并发现域名被用于钓鱼。
