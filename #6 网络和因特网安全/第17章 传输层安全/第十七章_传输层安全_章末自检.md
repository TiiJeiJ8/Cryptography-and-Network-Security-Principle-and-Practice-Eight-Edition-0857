# 第17章 传输层安全 — 章末学习目标自检

---

## 1. 能否按完整性、保密性、可用性和认证说明 Web 威胁、后果与对策？

Web 需要专门安全工具的原因：底层软件复杂潜藏漏洞；Web 服务器通常连接企业内部系统，被攻陷可扩大为整站入侵；普通用户安全意识有限。

| 安全目标 | 典型威胁 | 可能后果 | 常用对策 |
| --- | --- | --- | --- |
| **完整性** | 修改用户数据、特洛伊木马浏览器、修改内存或传输中消息 | 信息丢失、机器受损、引入更多攻击 | 加密校验和、完整性保护 |
| **保密性** | 网络窃听、窃取服务器/客户端数据、窃取配置和通信内容 | 信息泄露、隐私丧失 | 加密、Web 代理 |
| **可用性** | 破坏用户线程、伪造消息使机器溢出、填满磁盘或内存、DNS 攻击 | 中断、干扰、无法正常工作 | 难以完全防止，需检测和恢复 |
| **认证** | 冒充合法用户、伪造数据 | 用户作出错误决定、相信虚假信息 | 加密认证技术 |

被动攻击主要窃听通信；主动攻击伪装身份、修改消息或网站。按位置还可分为服务器、浏览器和通信链路上的威胁。

## 2. 能否比较 IPsec、TLS 和应用层安全在 TCP/IP 协议栈中的位置及取舍？

| 位置 | 例子 | 特点 | 取舍 |
| --- | --- | --- | --- |
| **网络层** | IPsec | 对终端用户和应用透明，可形成通用方案并过滤选定流量 | 粒度粗，无法区分应用；部署需内核/网络支持 |
| **传输层** | SSL/TLS | 可作为协议栈一部分对应用透明，也可嵌入浏览器和服务器软件 | 需应用支持 TLS；只保护 TCP 连接；可按进程/端口选择性保护 |
| **应用层** | S/MIME、Kerberos、应用专用安全 | 可按具体应用需求定制，处理消息级语义 | 每个应用需分别实现安全功能，不通用 |

## 3. 能否区分 TLS 会话、TLS 连接、当前状态和挂起状态？

| 概念 | 含义 |
| --- | --- |
| **TLS 连接** | 对等实体之间短暂的传输关系；每个连接关联一个会话，独立维护随机数、读写 MAC 密钥、读写加密密钥、CBC 的 IV 和从 0 递增的序号（不超过 $2^{64}-1$） |
| **TLS 会话** | 由握手创建的客户端-服务器关联，定义可由多个连接共享的密码安全参数：会话标识、对等实体 X.509v3 证书、压缩方法、密码规范、48 字节主密钥、是否可恢复标志 |
| **当前状态** | 已建立会话后实际用于读写的状态 |
| **挂起状态** | 握手期间创建，握手完成（收到 ChangeCipherSpec）后复制为当前读写状态 |

会话与连接是**一对多复用**关系：一个会话可关联多个连接，连接生命周期短、会话保持较长时间，从而把昂贵的 DH 密钥交换或 RSA 解密开销分摊到多个连接上。

## 4. 能否写出 TLS 记录协议的处理顺序，并说明 MAC 覆盖哪些字段？

发送方向依次执行：

```text
应用消息 → 分段（每段不超过 2^14 字节）→ 可选无损压缩
→ 计算 HMAC → 对数据与 MAC 加密并按分组密码规则填充
→ 加 5 字节 TLS 头部 → 交给 TCP
```

TLS 使用 HMAC：

$$\mathrm{HMAC}_K(M) = H\bigl[(K^+ \oplus \mathrm{opad}) \parallel H[(K^+ \oplus \mathrm{ipad}) \parallel M]\bigr]$$

**MAC 输入覆盖的字段**：

$$\mathrm{MAC\_write\_secret} \parallel \mathrm{seq\_num} \parallel \mathrm{type} \parallel \mathrm{version} \parallel \mathrm{length} \parallel \mathrm{fragment}$$

- `seq_num`：防重放；
- `type`：绑定记录内容类型，防类型混淆；
- `version`：版本字段也被保护，能发现协议版本被篡改；
- `length` 和 `fragment`：保护长度和数据本身。

记录头部包含内容类型、主版本号、从版本号和压缩长度；内容类型可为 `change_cipher_spec`、`alert`、`handshake` 或 `application_data`。分组密码填充长度可变且为分组长度整数倍，可在一定程度上阻止基于消息长度的分析。

## 5. 能否说明修改密码规范协议、警报协议和握手协议分别承担什么职责？

| 协议 | 职责 |
| --- | --- |
| **修改密码规范协议** | 只有一个值为 1 的字节；收到后把挂起密码状态复制为当前状态，后续记录改用新协商的密码组。它是状态切换的显式信号 |
| **警报协议** | 每条消息 2 字节：第一字节为警告（1）或致命（2），第二字节描述具体错误。致命警报立即终止当前连接，但会话中其他连接可继续 |
| **握手协议** | 在应用数据传输前执行，完成相互认证、协商协议版本、密码组、压缩方法、MAC 算法，并生成保护记录层的密钥 |

握手消息由类型（1 字节）、长度（3 字节）和内容组成，常见类型包括 `client_hello`、`server_hello`、`certificate`、`server_key_exchange`、`certificate_request`、`server_done`、`client_key_exchange`、`certificate_verify` 和 `finished`。

## 6. 能否按四阶段描述 TLS 握手，并说明 RSA、固定 DH、瞬时 DH 和匿名 DH 的认证差异？

| 阶段 | 内容 |
| --- | --- |
| **1. 建立安全能力** | ClientHello 发送最高版本、客户端随机数、会话 ID、密码组列表、压缩方法；ServerHello 返回服务器随机数、会话 ID、选定密码组和压缩方法 |
| **2. 服务器认证和密钥交换** | 服务器发送 X.509 证书；按密钥交换方法可能发送签名的临时 RSA/DH 参数、证书请求，最后发 `server_done`。签名哈希包含两个 Hello 随机数和服务器参数，防重放与伪装 |
| **3. 客户端认证和密钥交换** | 客户端验证服务器证书；若被请求则发送自己的证书；发送 `client_key_exchange`（RSA 时为用服务器公钥加密的 pre_master_secret）；可用 `certificate_verify` 证明拥有客户端私钥 |
| **4. 完成** | 双方依次发送 `change_cipher_spec` 和加密的 `finished`，验证握手过程完整后开始传输应用数据 |

四种密钥交换的认证差异：

| 方式 | 认证情况 | 安全性 |
| --- | --- | --- |
| **RSA** | 用服务器证书公钥加密 pre_master_secret，认证服务器 | 无 DH 前向安全（私钥泄露可解密历史流量） |
| **固定 DH** | 证书中包含固定 DH 参数 | 参数固定，无每次握手新密钥 |
| **瞬时 DH（DHE/ECDHE）** | 每次握手生成临时 DH 参数并由服务器私钥签名 | **安全性最高**，提供前向安全 |
| **匿名 DH** | 不认证参数 | 容易受到中间人攻击 |

## 7. 能否写出 master_secret、key_block 和 PRF/P_hash 的核心公式？

先交换 `pre_master_secret`，再生成 48 字节主密钥：

$$\mathrm{master\_secret} = \mathrm{PRF}\bigl(\mathrm{pre\_master\_secret}, \text{``master secret''}, \mathrm{ClientHello.random} \parallel \mathrm{ServerHello.random}\bigr)$$

随后生成密钥块：

$$\mathrm{key\_block} = \mathrm{PRF}\bigl(\mathrm{master\_secret}, \text{``key expansion''}, \mathrm{server\_random} \parallel \mathrm{client\_random}\bigr)$$

从密钥块按顺序取出客户端/服务器写 MAC 密钥、写加密密钥和 IV。

PRF 由 HMAC 扩展函数 $P\_\text{hash}$ 构成：

$$P\_\text{hash}(\mathrm{secret}, \mathrm{seed}) = \mathrm{HMAC}(\mathrm{secret}, A(1) \parallel \mathrm{seed}) \parallel \mathrm{HMAC}(\mathrm{secret}, A(2) \parallel \mathrm{seed}) \parallel \cdots$$

其中 $A(0) = \mathrm{seed}$，$A(i) = \mathrm{HMAC}(\mathrm{secret}, A(i-1))$，且：

$$\mathrm{PRF}(\mathrm{secret}, \mathrm{label}, \mathrm{seed}) = P\_\text{hash}(\mathrm{secret}, \mathrm{label} \parallel \mathrm{seed})$$

标签和双方随机数把不同用途、不同连接、不同方向的输出分隔开，防止上下文混用。TLSv1.2 采用基于 SHA-256 的 PRF。

## 8. 能否比较 SSL、早期 TLS 与 TLSv1.3 在密钥交换、密码功能和握手往返次数上的差异？

| 比较点 | SSL/早期 TLS | TLSv1.3 |
| --- | --- | --- |
| **密钥交换** | 可用 RSA、固定/瞬时/匿名 DH | 只使用 DH 或 ECDH，移除静态 RSA 密钥交换，每次握手生成新协商密钥，提供**前向安全** |
| **密码功能** | 允许 RC4、旧式 MAC、压缩、重新协商、MD5/SHA-224 签名等历史功能 | 删除压缩、不提供认证加密的密码套件、静态 RSA/DH、32 位时间戳、重新协商、修改密码规范协议、RC4 |
| **握手往返** | 多阶段、多次往返（2-RTT） | 调整消息顺序缩短到**一次往返（1-RTT）**，减少延迟和攻击面 |
| **安全目标** | 依赖证书、随机数、MAC 和加密组合 | 减少攻击面、优先认证加密、强化前向安全 |

## 9. 能否说明 HTTPS 如何初始化和关闭 TLS 连接，以及为何需要 close_notify？

**初始化流程**：
1. 先建立 TCP 连接（默认端口 443）；
2. 由客户端 TLS ClientHello 启动握手；
3. TLS 握手成功后，客户端发出 HTTP 请求；
4. 所有 HTTP 数据（URL、文档、表单、Cookie、HTTP 头部）作为 TLS `application_data` 加密传输。

HTTPS 提供保密性、完整性和认证（通过网站证书确认连接到预期网站）。一个 TLS 会话可支持多个连接。

**关闭流程**：双方应通过 TLS 警报协议发送 `close_notify`，再关闭 TCP。只发送单方关闭警报称为**不完全关闭**。

**需要 close_notify 的原因**：若 TCP 在没有 `close_notify` 和 `Connection: close` 的情况下断开，客户端无法区分"对方正常结束"与"攻击者截断了数据流"，因此应产生安全警告——攻击者可能利用未通知的截断隐藏部分消息。

## 10. 能否列出 SSH 三个协议层的职责，并说明主机密钥如何认证服务器？

SSH2 建立在 TCP 之上，由三个协议层组成：

| 层 | 职责 |
| --- | --- |
| **SSH 传输层协议** | 服务器认证、保密性、完整性和可选压缩，可提供前向安全 |
| **SSH 用户认证协议** | 让用户向服务器证明身份 |
| **SSH 连接协议** | 在一条安全低层连接上复用多个逻辑信道 |

**主机密钥认证服务器**：服务器用主机公私钥对认证。客户端有两种信任方式：
- 维护"主机名—公钥"本地数据库（如 `known_hosts`）：无需集中设施，但首次连接需人工确认、维护开销大；
- 只信任 CA 根密钥并验证 CA 签发的主机证书：减少本地数据库，但要求所有主机密钥均由 CA 认证。

## 11. 能否描述 SSH 传输层的标识交换、算法协商、DH 密钥交换、NEWKEYS 和服务请求？

传输层依次进行：

1. **标识串交换**：双方交换版本标识字符串（如 `SSH-2.0-OpenSSH_...`）；
2. **算法协商**：互发 `SSH_MSG_KEXINIT`，协商密钥交换、加密、MAC、压缩算法；
3. **Diffie-Hellman 密钥交换**：客户端计算 $e = g^x \bmod p$，服务器计算 $f = g^y \bmod p$，双方得到共享主密钥：

$$K = e^y \bmod p = f^x \bmod p$$

服务器用主机私钥签名包含双方标识串、KEXINIT 消息、主机公钥、$e$、$f$ 和 $K$ 的哈希 $H$；客户端验证主机公钥和签名，完成服务器认证。由 $K$、$H$ 和会话标识派生双向 IV、加密密钥和完整性密钥；

4. **切换新密钥**：双方互发 `SSH_MSG_NEWKEYS`，此后数据包使用协商好的算法和派生密钥保护；
5. **服务请求**：客户端发送 `SSH_MSG_SERVICE_REQUEST` 请求用户认证或连接服务。

传输层数据包包含数据包长度、填充长度、净荷、随机填充和 MAC；协商加密后除 MAC 外整个数据包加密，MAC 覆盖数据包和隐式 32 位序号。

## 12. 能否区分 SSH 用户认证方法、连接信道和本地/远程端口转发？

**用户认证方法**（请求包含用户名、服务名和认证方法）：

| 方法 | 机制 |
| --- | --- |
| **公钥认证** | 客户端用私钥对挑战签名 |
| **口令认证** | 在传输层加密保护下发送口令 |
| **基于主机认证** | 由客户端主机私钥证明主机身份；不直接证明用户本人，而是信任已认证主机对用户的声明 |

服务器可返回失败、可继续的方法列表或"部分成功"标志；所需方法全部成功后返回 `SSH_MSG_USERAUTH_SUCCESS`。

**连接信道**：连接协议把一条安全连接复用为多条逻辑信道，每条信道有本地信道号、窗口大小和最大包长，类型包括会话、X11、前向 TCP/IP 和直接 TCP/IP。信道机制实现多路复用、每信道独立流控和资源隔离。

**端口转发**：

| 模式 | 监听位置 | 方向 |
| --- | --- | --- |
| **本地转发** | 客户端建立监听端口，截获本地应用流量送入 SSH 隧道，由远程 SSH 转发到目标服务 | 本地 → SSH 隧道 → 远程服务 |
| **远程转发** | 服务器侧监听端口，把流量经隧道送回客户端网络 | 远程 → SSH 隧道 → 客户端侧服务 |

两者共同作用是让原本没有密码保护的 TCP 应用借助 SSH 获得保密性、完整性和服务器认证。
