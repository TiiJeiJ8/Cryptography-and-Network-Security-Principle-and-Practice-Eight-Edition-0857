# 一、TLS 在 TCP/IP 协议栈中的位置

在标准的 TCP/IP 五层模型中，TLS 位于**传输层（TCP）之上、应用层之下**，属于会话层/表示层的功能范畴。

| 层级 | 协议/功能 | 说明 |
| --- | --- | --- |
| 应用层 | HTTP、FTP、SMTP 等 | 用户业务数据 |
| **表示层（TLS 层）** | **TLS 记录协议、握手协议、警报协议** | **安全加密层** |
| 传输层 | TCP（端口 443 用于 HTTPS） | 可靠传输、分段、流量控制 |
| 网络层 | IP（IPv 4/IPv 6） | 路由寻址、数据包转发 |
| 数据链路层 | 以太网/Wi-Fi 帧 | MAC 寻址、差错检测 |
| 物理层 | 比特流、电信号/光信号 | 物理介质传输 |

**关键结论**：传输层（TCP）的上层是应用层（含 TLS），下层是网络层（IP）。TLS 本身不是独立的一层，而是嵌入在应用层与传输层之间的安全子层。

# 二、TLS 协议栈架构

TLS 不是单层协议，而是由**两层协议**构成，如图 17.2 所示。

## 2.1 底层：TLS 记录协议（TLS Record Protocol）

- 为所有高层协议提供基本安全服务：**保密性**（加密）和**消息完整性**（MAC）
- 接收来自高层协议的数据，执行分段、压缩（可选）、计算 MAC、加密、添加头部，最终交给 TCP 传输
- 对上层是透明的服务提供者

## 2.2 上层：四个高层协议（运行于记录协议之上）

| 高层协议 | 功能 | 内容类型取值（十进制） |
| --- | --- | --- |
| **握手协议（Handshake Protocol）** | 客户端与服务器相互认证，协商加密算法、MAC 算法和主密钥 | 22 |
| **修改密码规范协议（Change Cipher Spec Protocol）** | 通知对方“从现在开始使用新协商的密钥” | 20 |
| **警报协议（Alert Protocol）** | 传递 TLS 相关的错误或关闭通知（致命/警告） | 21 |
| **心跳协议（Heartbeat Protocol）** | 保持连接活跃，检测对端是否在线（在单独 RFC 中定义） | 24 |

> **注意**：HTTP 不属于 TLS 专用协议，但 TLS 最常见的应用是承载 HTTPS（即 HTTP over TLS）。HTTP 数据同样作为应用数据由记录协议封装，内容类型取值为 23（Application Data）。

# 三、连接（Connection）与会话（Session）

## 3.1 定义

- **连接（Connection）** ：在 OSI 分层模型定义中，连接是指提供合适类型的服务的一种传输。对 TLS 来说，连接表示的是对等关系。连接是**短暂**的，每个连接都与一个会话关联。
- **会话（Session）** ：TLS 会话是指客户端和服务器之间的一个**关联**。会话是由握手协议创建的，它定义一组由多个连接共享的密码安全参数。

## 3.2 核心关系：一对多的复用

一个会话可以关联**多个**连接，但每个连接在任意时刻都只归属于一个会话。

**会话状态**由以下参数定义：

- 会话标识（Session ID）
- 对等实体证书（X.509.v 3）
- 压缩方法
- 密码规范（CipherSpec）
- **主密钥（Master Secret）** ：48 字节共享密钥
- 可恢复标志

**连接状态**由以下参数定义：

- 服务器/客户端随机数（各 32 字节）
- 服务器写 MAC 密钥、客户端写 MAC 密钥
- 服务器写密钥、客户端写密钥
- 初始化向量（IV）
- 序列号（防重放，每个连接独立维护）

## 3.3 设计目的

会话的创建开销较大（涉及完整的握手协商，如 Diffie-Hellman 密钥交换和证书验证），其设计目的是**避免为每次新连接重新执行完整的密钥协商过程**。通过会话复用，后续连接可快速恢复，将昂贵的密码学计算分摊到多个连接上。

# 四、TLS 记录协议详解

## 4.1 数据结构

TLS 记录的顶层格式如图 17.4 所示：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| 内容类型（Content Type） | 8 位 | 标识上层协议类型（20/21/22/23/24） |
| 主版本号 | 8 位 | TLS 1.2 为 3 |
| 从版本号 | 8 位 | TLS 1.2 为 3 |
| 压缩长度 | 16 位 | 明文/压缩后净荷的字节长度（≤2^14+2048） |
| 加密净荷（密文） | 可变 | 压缩后的高层协议消息 + MAC，经对称加密 |

## 4.2 操作流程（发送端）

1. **分段**：将上层消息切分为≤2^14 字节（16384 字节）的块
2. **压缩（可选）** ：无损压缩，长度增加不超过 1024 字节（TLS 1.2 默认无压缩，TLS 1.3 已移除压缩）
3. **计算 MAC**：使用 HMAC 算法（基于 MD 5 或 SHA-1），输入包括序列号、类型、版本、长度和明文片段
   $$
   \mathrm{HMAC\_hash}(\mathrm{MAC\_write\_secret}, \mathrm{seq\_num} \parallel \mathrm{type} \parallel \mathrm{version} \parallel \mathrm{length} \parallel \mathrm{fragment})
   $$
4. **加密**：使用对称加密（如 AES-CBC 或 AES-GCM）加密“明文片段 + MAC”
5. **添加头部**：写入内容类型、版本和长度，形成完整 TLS 记录，交给 TCP

## 4.3 接收端处理

1. 从 TCP 字节流中解析出 TLS 记录头部
2. 根据头部长度字段提取完整密文
3. 解密载荷，验证 MAC
4. 根据内容类型字段将解密后的明文分发给对应的上层协议（握手、警报或应用层）

# 五、TLS 在数据报文传输中的完整应用过程

以下以 HTTPS 访问网页为例，详细说明一条消息如何从应用层发往网络。

## 5.1 阶段一：建立 TCP 连接（传输层）

客户端与服务器完成 TCP 三次握手（SYN → SYN-ACK → ACK），建立可靠字节流通道。此时管道为明文，尚未涉及 TLS。

## 5.2 阶段二：TLS 握手（安全协商）

**步骤 1：客户端发送 `ClientHello` **
- 上层：握手协议生成 `ClientHello` 消息（含 TLS 版本、密码套件列表、客户端随机数）
- 记录协议：将该消息作为载荷，头部 `Content Type = 22`（Handshake），加密前明文发送（因密钥尚未协商）
- 下传至 TCP，封装为 TCP 段发出

**步骤 2：服务器回复 `ServerHello`、`Certificate`、`ServerKeyExchange`、`ServerHelloDone` **
- 同样由握手协议生成，记录协议以明文封装（`Content Type = 22`）发给客户端
- 服务器返回选定的密码套件、服务器随机数、证书链及 Diffie-Hellman 公钥参数

**步骤 3：客户端发送 `ClientKeyExchange`、`ChangeCipherSpec`、`Finished` **
- 客户端验证服务器证书后，发送客户端 Diffie-Hellman 公钥参数（`ClientKeyExchange`）
- 双方各自计算预主密钥（pre_master_secret）和主密钥（master_secret）
- 客户端发送 `ChangeCipherSpec` 记录（`Content Type = 20`，载荷为单字节 `0x01`），告知“即将切换加密”
- 客户端发送 `Finished` 记录（`Content Type = 22`，但此时**载荷已加密**，使用新协商的主密钥和算法），该消息包含之前所有握手消息的哈希值，用于验证握手未被篡改

**步骤 4：服务器回复 `ChangeCipherSpec` 和 `Finished` **
- 服务器同样发送 `ChangeCipherSpec` 并切换加密
- 服务器发送加密的 `Finished` 消息
- 握手完成，进入安全数据传输状态

## 5.3 阶段三：加密数据传输（记录协议 + TCP 协作）

1. **应用层**：浏览器生成 HTTP 请求（如 `GET /index.html HTTP/1.1`）
2. **TLS 记录协议**：
   - 将 HTTP 数据作为载荷，头部 `Content Type = 23`（Application Data）
   - 计算 MAC、加密（密文 = 加密(HTTP 载荷 + MAC)）
   - 形成完整 TLS 记录（明文头部 + 密文载荷）
1. **传输层（TCP）** ：
   - 将 TLS 记录密文字节流放入 Socket 发送缓冲区
   - 根据 MSS（最大分段大小）将字节流切分为多个 TCP 段
   - 为每个段添加 TCP 头部（含源端口 443、目的端口、序列号、确认号、校验和、标志位）
   - 将段加入发送队列，启动重传计时器
1. **网络层（IP）** ：添加 IP 头部（源 IP、目的 IP、协议号=6），封装为 IP 数据包
2. **数据链路层**：添加 MAC 头部（源/目的 MAC 地址）和尾部（FCS 校验），封装为帧
3. **物理层**：将帧转换为比特流，调制成电/光/电磁信号发出

## 5.4 阶段四：接收端反向处理

1. 物理层→链路层：还原帧，剥离 MAC 头部，将 IP 数据包交给网络层
2. 网络层：剥离 IP 头部，根据协议号=6 将 TCP 段交给传输层
3. 传输层（TCP）：
   - 检查校验和，丢弃错误段
   - 根据序列号对乱序到达的段排序，回复 ACK 确认
   - 将载荷字节流按序放入接收缓冲区，通过 Socket 接口上交
1. TLS 记录协议：
   - 解析记录头部，提取完整密文段
   - 解密载荷，验证 MAC
   - 根据头部 `Content Type` 字段决定分发目标：23 交给 HTTP，22 交给握手协议，21 交给警报协议
1. 应用层：HTTP 协议处理解密后的明文请求，生成响应，反向重复上述流程

## 5.5 阶段五：连接关闭（警报协议）

任一方希望关闭安全连接时，发送一条警报记录（`Content Type = 21`），载荷为 `close_notify` 消息（加密发送）。然后才关闭 TCP 连接（四次挥手）。

# 六、关键概念辨析

## 6.1 “逻辑分层”与“数据封装”的关系

- **逻辑分层（调用关系）** ：握手协议、警报协议、HTTP 等**运行在记录协议之上**，即它们是记录协议的“用户”，调用记录协议提供的安全服务。
- **数据封装（处理顺序）** ：当高层协议产生一条消息后，它将消息**下传**给记录协议。记录协议将其视为载荷，执行分段→压缩→MAC→加密→加头，最终生成一条 TLS 记录。

**两个视角并不矛盾**：记录头部的 **内容类型（Content Type）** 字段是连接二者的桥梁——它在封装时标明载荷来源于哪个上层协议，在接收端解密后，该字段告诉系统将数据交还给哪个上层协议处理。

## 6.2 连接与会话的区分

| 维度 | 连接（Connection） | 会话（Session） |
| --- | --- | --- |
| 本质 | 实际数据传输通道 | 安全参数共享上下文 |
| 生命周期 | 短暂 | 持久 |
| 状态 | 独立维护随机数、密钥、IV、序列号 | 共享主密钥、证书、密码规范 |
| 复用关系 | 每个连接属于一个会话 | 一个会话可支持多个连接 |
| 目的 | 承载具体通信 | 避免重复昂贵协商 |
